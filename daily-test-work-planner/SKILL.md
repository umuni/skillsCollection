# 每日测试工作计划

## 执行流程

1. 将用户输入按独立交付物切分为原始任务，不要把多个不同事项挤进一条。
2. 读取 [事项分类与模板](references/task-templates.md)，为每项任务匹配一个主分类；无法唯一匹配时，先询问任务目标或交付物。
3. 用5W3H检查信息，但只追问影响执行或工时的缺口。内部检查字段：
   - What：对象、范围、交付物。
   - Why：目标、风险或优先级。
   - Who：执行人、协作方、验收人。
   - When：开始时间、截止时间、依赖时间。
   - Where：环境、端、版本或平台。
   - How：步骤、策略、工具或完成标准。
   - How many：模块、流程、功能点、用例、接口、数据组合、缺陷或平台数量。
   - How much：净工时、缓冲及估算依据。
4. 按分类模板检查必填信息。只要缺少“对象/范围、产出或完成标准、至少一个规模量”中的任一项，停止生成计划并追问。
5. 信息充分后拆成0.5至4小时的执行块；超过4小时继续按模块、阶段、风险或交付物拆分。预研类任务拆到“大任务下的子任务”即可，子任务以检索、样例验证、方案记录、结论输出等独立产出为边界，不强行细化到操作步骤。
6. 按“基准耗时 × 数量 × 复杂度系数 + 固定准备时间”估算净工时，再按风险增加10%至30%缓冲。基准仅作参考，优先使用用户历史数据或团队口径。
7. 按依赖关系排序：澄清/准备 → 设计 → 执行 → 缺陷/回归 → 交付/复盘。并行任务标注可并行，不虚构具体时间点。
8. 生成最终计划后运行 `python scripts/validate_plan.py <计划文本文件>`；校验失败时压缩或补齐后再输出。

## 追问规则

- 一次只问当前批次最关键的1至3个问题，合并同类任务的重复问题。
- 优先追问规模量，其次追问范围/环境，再追问截止时间、依赖和完成标准。
- 用户不知道精确数量时，允许提供区间、小/中/大复杂度或历史相似任务；明确标记为暂估。
- 不要在同一轮既追问又输出假定后的正式计划。

追问格式：

```text
补充以下信息后才能准确拆解：
1. [任务名]：涉及几个模块/主流程/功能点？
2. [任务名]：目标环境、版本及完成标准是什么？
```

## 工时估算

读取 [估算基线](references/estimation-baselines.md)。按以下优先级选依据：

1. 用户或团队历史实测数据。
2. 本次明确的数量及复杂度。
3. 参考基线，并标记“暂估”。

不要使用“根据经验”“工作量适中”等不可核验表述。会议、等待构建、环境排障和跨团队确认应与实际测试工时分开。

## 输出约束

- 只输出可执行计划，不展开完整5W3H分析。
- 每个执行块独占一行，序号不计入任务正文也可以，但正文必须不超过75个字符；为稳定起见优先控制在65个字符内。
- 每行必须同时包含：具体动作及对象、评估工时、至少一个量化依据。
- 推荐格式：`动作+对象｜工时Xh｜依据：数量/复杂度`。
- 预研类推荐格式：`【预研】大任务-子任务｜工时Xh｜依据：验证点/数据源/复杂度`。
- 工时使用`0.5h`、`1h`、`1.5h`等0.5小时粒度；无法准确估算时使用范围并标注暂估。
- 不输出空泛事项，如“跟进需求”“执行测试”“处理问题”。
- 多项任务最后增加一行总工时；总工时行也不得超过75个字符，并说明是否含缓冲。
- 若计划超过当日可用工时，明确给出优先级和顺延项，不通过压缩工时制造可行性。

示例：

```text
1. 评审支付退款需求并记录疑点｜1.5h｜依据：2模块、3主流程、12功能点
2. 设计退款主流程与异常用例｜2.5h｜依据：3流程、12功能点、预计30例
3. 验证退款缺陷并回归关联链路｜1.5h｜依据：5个缺陷、2条关联流程
总计5.5h（含约0.5h风险缓冲）
```

## 质量检查

输出前逐项确认：

- 分类与任务真实意图一致。
- 每项都有明确对象、动作、完成边界。
- 每项都有工时和可复核的数量依据。
- 任务顺序满足依赖且单项不超过4小时。
- 未擅自补造模块数、用例数、缺陷数或截止时间。
- 每行不超过75个字符。
