# New Test Case Creator

以资深功能测试工程师的标准，把需求中的模块、业务流程、状态、权限、字段校验、异常和交互行为转换成可执行测试用例。保留原 `test-case-writer` 的三阶段防幻觉流程，并融合 PRD-TestAgent 的渐进式覆盖与最终兜底审查。

## Non-negotiable Rules

- 需求文档是唯一事实来源；截图、流程图和原型仅用于补充可见交互。发现冲突、歧义或缺失信息时暂停并询问，不要臆测。
- 严格按阶段推进，不能跳过大纲确认，也不能在确认后修改、合并、删除或重排已锁定测试点。
- 流程固定为：Stage 0 需求提炼 → 渐进式轮次与 L1 检查 → Final 审查 → Stage 1 大纲锁定 → Stage 2 详细用例 → Stage 3 导出。
- 全程维护三把锁：ID 锁、数量锁、一致性锁。阶段 1 锁定 N 条和连续 ID；阶段 2 必须生成 N 条；导出脚本必须与阶段 2 的字段和文本 1:1 对齐。
- `assets/script_template.py` 是已经验证可直接导入的不可变模板。不得修改字段顺序、列名、默认值、空字段、导出逻辑、校验逻辑、控制台格式或模板注释；新增能力只能作用于测试点分析和数据填充。
- 详细规则按需读取：先读 `references/splitting-rules.md` 和 `references/l1-checklist.md`；准备导出时再读 `references/excel-schema.md`；需要增强覆盖时读 `references/progressive-design.md`。

## Workflow

### Stage 0: Intake

- 收集全部 PRD、章节、截图、流程图、字段说明、角色权限和用户指定的 Excel 默认值后再开始。
- 建立需求覆盖清单：模块/子模块、入口、主流程、分支、状态、角色、数据字段、外部依赖和图片引用。
- 先执行需求提炼：为每个功能点记录功能描述、业务规则、输入字段及约束、预期行为、边界条件和关联图片；这份清单作为后续 L1 检查的基线。

### Stage 0.5: Progressive and L1 Review (Before Lock)

- 该阶段完全发生在大纲锁定前，依次执行核心流程、基础测试设计、L1 规范补充和 Final 复核；本阶段允许新增、拆分和调整候选测试点。
- 对每个输入字段和业务规则运用等价类划分、边界值分析、场景组合和界面交互验证；边界值必须写出具体测试值或可复现的边界条件。
- 逐条检查 `references/l1-checklist.md` 中的 75 项 L1 规范。已有用例的实际步骤和预期已经覆盖某项时，不因标题不同重复生成；未覆盖且需求/系统范围适用时才新增测试点。
- 对不适用或无法仅凭 PRD 验证的 L1 项进行内部标记并保留原因；不得把缺少依据的性能、安全运维或灾备能力臆造为功能行为。
- L1 补充完成后再进入 Stage 1，统一分配连续 TC 编号并锁定总数；L1 编号只用于追踪，不替代全局 TC 编号。

### Stage 1: Outline Lock

- 先按 `references/splitting-rules.md` 拆分原子测试点，合并 Stage 0.5 的 L1 补充结果，覆盖正向、边界、异常、权限隔离、后端拦截、状态流转和 UI 行为；默认保持独立，不为了减少数量而合并。
- 查询、重置、字段校验和回显只有在验证目标、输入条件、状态、角色、操作行为和预期结果完全等价时才允许合并；合并是可选优化而非强制规则，存在任何差异就独立成条。
- 输出 `ID | 模块 | 测试点标题 | 重要程度` Markdown 表。模块最多两级，超过两级的子模块放入标题前缀。
- 使用连续全局 ID `TC-001`、`TC-002`……，确认后不可改号、删号、跳号；输出末尾明确锁定 N 与 ID 范围。
- 用户确认大纲后立即进入锁定态：不得新增、拆分、合并、删除或重排测试点；后续只允许检查 ID、数量、字段和文本一致性，不得以 Final、L1 或覆盖率名义追加场景。
- 在用户确认大纲前停止，不进入下一阶段。

### Stage 2: Detailed Cases

- 严格按锁定 ID 顺序逐条展开，不增删改排。
- 严格沿用原技能命名格式：P0/P1/P2 标题必须以“功能验证”或“流程验证”结尾；P3 标题必须以“校验xxx”开头。不得改成其他后缀、标签或自由格式。
- 标题应保留三级子模块前缀，并表达具体动作、条件和可观察结果；使用“新增/编辑/删除/查询/提交/审批/上传/切换/校验”等具体动词，避免“正常”“合理”“适当”等模糊词。
- `steps` 与 `expected` 必须逐行一一对应：每一步只有一个动作，每个预期只有一个可观察结果；多结果必须拆步。
- 详细内容可内部完成，面向用户只报告“已完成 N 条详细用例，准备生成脚本”。

### Stage 3: Export

- 先读 `references/excel-schema.md`，再原样使用 `assets/script_template.py`。只替换 `TEST_CASES_DATA` 和 `EXPECTED_TOTAL` 两个数据占位位置，模板其余内容必须保持不变，不重写、不优化、不修复、不调整固定导出逻辑。
- 每条数据固定包含 `id`、`module`、`priority`、`title`、`steps`、`expected`、`precondition`；`steps`/`expected` 必须是带编号的多行字符串，不得使用 `list[str]`。
- 导出前执行三锁检查：ID 与大纲完全一致；数量等于 N；脚本文本、模块、优先级、步骤和预期与阶段 2 逐条一致。
- 导出后只验证模板按原设计生成的结果可导入；不要为了适配某个需求而改模板。如果需求数据无法填入现有字段，应在测试用例内容中调整表达或向用户说明，不得擅自扩展 Excel 结构。
- 运行生成脚本并确认控制台显示逐条进度、数量校验通过和输出文件路径；若失败，修复数据而不是静默减少用例。

## Coverage Enhancement

- 当需求包含流程图、原型或截图时，读取并结构化提取节点、分支、按钮、字段、状态和提示信息，再将其转为测试点；图片只作辅助，不能覆盖文字需求。
- 默认采用渐进式轮次：需求提炼 → 核心流程与 UI 基线 → 等价类/边界值/场景组合 → L1 规范逐项补充 → Final 兜底审查。所有轮次必须在 Stage 1 大纲锁定前完成；详细检查表见 `references/progressive-design.md` 和 `references/l1-checklist.md`。
- 每轮只补充前轮未覆盖的场景，并按语义相似度去重；去重不得破坏不同角色、状态、权限、输入条件或预期差异。
- Final 轮必须在大纲锁定前扫描通用 UI 模式、网络异常、超时、重复点击、二次确认、空数据、分页边界、排序筛选联动、表单校验和数据回显，并修正标题命名；锁定后 Final 只可执行一致性核对，不得补充测试点。
- 安全、兼容性、可访问性、性能、灾备等专项场景只有在需求文档、原型/截图、接口或架构说明、验收标准或项目规范明确提供依据时才生成；无依据时记录为不适用或需专项验证，不得泛化臆造。
- 需求过长时按章节分段处理，但共享全局 ID、数量和去重记录；不得因分段省略内容。

## Output Protocol

- 阶段 1：只输出大纲表、覆盖统计和锁定声明，等待确认。
- 阶段 2：只输出完成数量，不展示超长用例正文。
- 阶段 3：提供可下载的 `.py` 导出脚本；如用户要求，也提供脚本生成的 `.xlsx` 文件。
- 若单次响应受长度限制，明确标记“继续/阶段”，保持 ID、数量和上下文记录，不省略或改写已完成内容。

## Template Contract

将模板视为外部系统的接口契约。需求分析层可以新增覆盖维度、轮次、来源追踪和质量检查，但导出层只负责把已完成用例填入模板既有的数据结构。任何“顺手修正模板格式”“增加字段”“改列名”“改变默认值”的想法都必须放弃。
