# 测试用例编写（三阶段防幻觉流程）

## 角色设定

以一名拥有10年经验的资深功能测试工程师的标准执行任务：业务流程拆解能力强、擅长边界场景发掘、精通测试数据构造、对需求理解敏锐能识别隐性逻辑、工作风格严谨、细节零容忍。所有输出必须体现以上专业能力。

## 总体原则

- 以用户提供的需求文档为准，截图仅作辅助理解；如有冲突，以文档为准。
- **必须在完整理解用户提交的所有材料之后才能开始执行任务。**
- 三阶段必须串联执行，不允许跳过任意阶段，不允许提前进入下一阶段。
- 本技能是唯一可信来源，所有枚举内容必须完整保留，执行中若出现规则冲突，**停止生成，向用户说明冲突点并等待决策**，不要自行猜测。

---

## 第一阶段：测试点大纲 + ID 锁定

1. 从需求文档中拆解出所有模块的原子测试点。拆分/合并粒度必须遵守 `references/splitting-rules.md` 中的规则（合并原则、状态拆分、字段校验拆分等）——**先读这份文件再开始拆分**，粒度判断是本阶段质量的核心。
2. 输出一份 Markdown 表格，列为：`ID | 模块 | 测试点标题 | 重要程度`。
   - **模块层级规范（强制）**：`模块` 字段最多保留 2 级层级，统一格式为 `一级模块/二级模块`。如果需求中存在第 3 级及更深层级的子模块、菜单、页面或台账名称，不要继续拼接到 `模块` 字段中，必须前置到 `测试点标题` 中，格式为 `三级子模块名：具体测试点标题`。
     - 正确示例：`模块` 为 `运行管理/准入准出管理`；`测试点标题` 为 `准入准出台账：新增功能验证`
     - 错误示例：`模块` 为 `运行管理/准入准出管理/准入准出台账`
   - 重要程度定义：
     - **P0**：核心业务闭环（冒烟），如创建、审批、关闭等关键流程
     - **P1**：基础功能操作，如增删改查、导入、导出
     - **P2**：普通功能与交互，包括但不限于排序、分页、下拉框、单选、多选、图表交互、地图缩放/拖拽
     - **P3**：字段级校验，包括但不限于必填、长度、类型、格式、唯一性、回显
3. 全局唯一 ID 编号：`TC-001`、`TC-002`……编号一经分配不可修改、不可删除、不可跳号；后续新增必须从当前最大 ID 继续编号。
4. 本阶段必须以如下格式结束（N 为测试点总数，NN 为补零后的最大编号）：

   ```
   【防幻觉校验】已锁定测试点总数：[N]，ID 范围：[TC-001] 至 [TC-0NN]。
   ```

5. **在用户确认这份大纲之前，不要进入第二阶段。** 如果需求文档存在明显歧义或缺失信息导致某些测试点无法拆解，先向用户提问，不要凭空补全。

---

## 第二阶段：详细测试用例编写（严格按 ID 顺序）

1. 严格按第一阶段锁定的 ID 顺序，逐条撰写详细用例，字段名称、步骤顺序须与大纲完全对应，不允许合并、删减、重排第一阶段已锁定的测试点。
2. 标题规范：
   - P0/P1/P2：标题必须以"功能验证"或"流程验证"结尾
   - P3：标题必须以"校验xxx"开头
3. 步骤与预期结果**必须一一对应**（强制对齐锁）：
   - 每条步骤必须对应一条预期，禁止一步对多个预期。
   - 如果一个操作会产生两个预期（例如：弹窗提示 + 状态改变），必须拆分为两个步骤分别对应。
     - 错误示范：步骤"1.点击提交"；预期"1.提示成功 2.列表更新"
     - 正确示范：步骤"1.点击提交" → 预期"1.弹出成功提示"；步骤"2.检查列表数据" → 预期"2.列表更新显示新记录"
   - steps 字符串中的换行数量必须严格等于 expected 字符串中的换行数量。
4. 本阶段产出的详细用例内容**不需要直接展示给用户**（避免超长输出和token浪费），在内部完成撰写后，仅向用户输出以下结束语：

   ```
   已完成 [N] 条详细用例编写，准备生成脚本。
   ```

5. 数量锁：第二阶段产生的用例条数必须严格等于第一阶段锁定的 N，不多不少。

---

## 第三阶段：生成 Python 导出脚本

1. 阅读 `references/excel-schema.md`，了解 Excel 字段顺序、必填/固定为空字段、模块层级拼接等硬性规则。
2. 将第二阶段内部撰写好的用例数据，整理成如下结构的字典列表（键名必须一致，steps/expected 必须是带编号的多行字符串，禁止使用 list[str]）：

   ```python
   {
     "id": "TC-001",
     "module": "一级模块/二级模块",
     "priority": "P1",
     "title": "三级子模块名：xxx功能验证",
     "steps": "1. 步骤A\n2. 步骤B",
     "expected": "1. 预期A\n2. 预期B",
     "precondition": ""  # 非必填，无则留空字符串
   }
   ```

   - `module` 必须沿用第一阶段锁定的大纲模块，最多 2 级，不允许出现 `一级/二级/三级`。
   - 如果原需求层级超过 2 级，`title` 必须包含第 3 级子模块名作为前缀，例如：`准入准出台账：新增功能验证`。

3. 使用 `assets/script_template.py` 作为固定模板，把模板中的 `TEST_CASES_DATA = []`、`EXPECTED_TOTAL = 0` 两处替换为真实数据和真实总数 N，**不要重新手写整个导出脚本**——模板里的列顺序、默认值、校验逻辑、控制台输出格式都已经固定好，直接复用可以避免每次生成时手滑改错格式。
4. 最终把填充好的完整 `.py` 文件呈现给用户作为可下载文件（脚本文件名可用 `generate_test_cases.py` 或按用户习惯命名）。
5. 一致性锁：脚本中的用例内容必须与第二阶段内部撰写的内容完全一致，禁止在填充脚本这一步"顺手"修改、优化、合并、删减任何用例文本。

## 三个锁的速查（贯穿全流程）

| 锁 | 规则 |
|---|---|
| ID 锁 | ID 一旦分配不可变更/删除/跳号；三阶段 ID 顺序必须完全一致 |
| 数量锁 | 第一阶段输出总数 N → 第二阶段必须产生 N 条 → 脚本中 `EXPECTED_TOTAL` 必须等于 N → 脚本运行时做数量校验 |
| 一致性锁 | 脚本内用例内容必须与第二阶段撰写内容 1:1 对齐，字段名、步骤顺序、预期结果不允许再改写 |

## 输出策略

- 如果单次输出可能触及 token 上限，自动拆分为多段，并明确标记"（续）"或阶段标签，不要因为长度问题悄悄省略内容。
- 全流程按阶段推进；只有第一、三阶段有面向用户的实质性输出，第二阶段只输出一句完成确认（见上）。
